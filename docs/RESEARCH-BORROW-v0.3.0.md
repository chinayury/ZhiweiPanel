## 一、本轮实施项的来源与依据

| 项 | 来源 | 排期轨迹 |
|----|------|---------|
| 审计导出 CSV/JSON | 等保合规的通用报表需求（"向监管提交操作审计记录"）；1Panel 提供日志导出 | v0.1.4 轮列为 P1（工作量小）→ v0.1.5 轮提为下一轮首位 → 本轮落地 |

实施前的实现核对（上一轮教训：排期前先读实现）：`git grep audit-logs` 确认
列表端点已存在、`ListAuditLogs` 有 1000 行钳制（导出不能复用）、
`auditMiddleware` 只记写方法（导出留痕需要显式写）——三个实现事实决定了本轮的设计。

## 二、可借鉴要点（本轮落地）

### A. 导出文件的表格软件兼容性（通用实践）

| 要点 | 通行做法 | 落地 |
|------|---------|------|
| 中文 CSV 必须带 **UTF-8 BOM** | 无 BOM 时 Excel 按本地编码解码，中文直接乱码 | ✅ 输出前置 `EF BB BF`，并有测试锁死 |
| 下载文件名含时间戳 | 便于多次导出并存、归档检索 | ✅ `zhiweipanel-audit-<时间>.<格式>` |
| 大结果集不走列表接口的钳制 | 列表接口为防误用钳行数，导出是显式行为 | ✅ 新增 `ListAuditLogsExport` 不设上限（安全性由审计表自身的 5000 条裁剪保证，注释里写明两条 API 的分工） |

### B. 敏感读操作也要留痕（1Panel / 主流审计实践）

"谁把审计日志拿走了"与"谁动了配置"同等重要——导出审计日志是典型的
**读但敏感**操作（数据外带）。落地：导出成功后显式写 `audit.export`
（操作者 / 格式 / 行数），留痕失败不影响导出主流程。

**取舍**：没有把「读但敏感」做成通用机制（如路由级注解），本轮只有一个这样的
端点，手工留痕 + 测试锁死即可；等出现第二个敏感读端点再抽象——
"只有一个使用方时抽象层是纯负债"（v0.2.2 轮确立的原则）。

### C. 前端下载交互复用既有形态

审计导出用 `window.open` + 会话 Cookie（与备份下载完全一致），不引入
fetch-Blob-ObjectURL 那套：下载是浏览器原生行为，文件名交给
`Content-Disposition`。零新前端基建。

## 六、一句话结论

> 审计做了三版（记录 → 留痕上限 → 导出），到本轮才算闭环：
> 等保场景要的是"能把记录交给监管"，此前只有"记录在库里"。
> 设计上最值得记的是两条克制——不为单端点抽象"敏感读"机制、
> 不给导出单独开写权限要求——都延续"只有一个使用方时抽象是负债"的项目原则。
