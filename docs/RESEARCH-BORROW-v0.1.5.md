## 一、本轮关键发现：已知限制清单腐烂（文档漂移）

上一轮把「README 已知限制 #14 / #15 的 UI 化」列为下一轮 P0。本轮实施前按惯例先读实现，
**发现两项功能早已完整实现**，上一轮的排期是基于陈旧文档的误判：

| 上一轮认知（README 原文） | 本轮核实结果 |
|------|------|
| #14「建立防篡改基线」只有 API，没有界面入口 | `site-detail.js` 防复改页签有「建立防篡改基线」按钮（含脏检查 / 启用检查 / 确认弹窗），`api.js` 有对应 helper，后端 `POST /api/sites/{id}/baseline` 返回 `{files:n}` 与前端一致 |
| #15 `shell` scope 只能通过 API 授予 | `ops.js` Token 创建弹窗有三个独立授权位（read / write / shell），shell 蕴含 write 的派生逻辑与注释齐全，列表页用 `danger` 色标签展示 Shell 权限 |

**验证方法**（不只看源码，看运行中的部署实际下发了什么）：
对测试环境运行中的面板 `curl` 其静态资源——`/js/views/site-detail.js` 含
`doEstablishBaseline` 与「建立防篡改基线」、`/js/views/ops.js` 含 `wantShell` 与
「可执行 Shell 计划任务（shell）」、`/js/api.js` 含 `establishBaseline`。三处全部命中。

**处置**：README「已知限制」移除 #14 / #15（16 条 → 14 条，重新编号）；
CHANGELOG v0.1.5 记录本次修正。`RESEARCH-BORROW-v0.1.4.md` 作为历史计划文档**不改写**
（它如实记录了当时的认知与依据），由本文负责勘误。

**方法论教训**：借鉴清单里「待实现」的条目，下一轮实施前必须先读实现——
文档清单会腐烂，`git grep` 五分钟就能避免一轮无效排期。

## 二、可借鉴要点（本轮落地）

### A. 面板可被 AI agent 安全操作（来源：goinfinite/os 的 SKILL.md / AGENTS.md 范式）

v0.1.4 轮已列为 P1 候选，本轮落地：

| 要点 | 做法 | 落地 |
|------|------|------|
| 面向机器的能力说明书 | 把「能做什么 / 哪些有副作用 / 有哪些坑」写成结构化文档 | ✅ 新增 `docs/AGENT.md`：认证与 scope 语义、有副作用端点速查（含 ★shell 标注）、只读端点、8 条运行时约定、agent 行为红线 |
| 红线可直接写进 agent 系统提示 | goinfinite 把危险操作显式列出 | ✅ 第 6 节：删站 / 改基线 / 恢复配置 / 建 shell Token / 跑 Shell 任务五类操作需人工确认 |

关键表述均经源码核实：Token 鉴权头（`Authorization: Bearer` / `X-API-Token`，裸 token 也接受）、
scope 派生（shell 蕴含 write）、PUT 全量替换语义（`UpdateSite` 直接保存解码后的完整对象）、
202 ≠ 201（建站落库但下发失败的区分）。

### B. CI 验证盲区加固（来源：上轮事故形态复盘 + 同类面板 CI 通用实践）

上轮已发现「CI 的 Docker 健康检查只验面板 API，验不出容器内 nginx 没运行」。
本轮在 `ci.yml` Docker job 补三条断言：pid 文件指向的 master 进程存活（`kill -0`）、
`nginx -t` 通过、启动日志无「初始配置下发失败」。

### C. 文档一致性要不要上门禁？（讨论后不落地）

理论上可以给「已知限制清单」做实现一致性检查，但：限制条目多为运行时行为
（需要起服务逐条探测），自动化成本远超收益。**取舍**：维护轮次的人工巡检
（先读实现再排期 + 部署侧实机抽查）已覆盖此类漂移，不为它加门禁。
