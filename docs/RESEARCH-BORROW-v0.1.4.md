## 二、可借鉴要点（深读提炼）

### A. 发布工程（本轮落地）

**来源**：`1Panel` 的 GitHub Release 实践、`hestiacp` 的版本化安装脚本、
`usememos` 等单二进制 Go 项目的通用发布惯例（GoReleaser 生态的标准形态）。

| 要点 | 同类项目做法 | 对 ZhiweiPanel 的价值 |
|------|-------------|-------------------|
| 产物由 **tag 触发**自动构建 | 通行做法：推 `vX.Y.Z` 标签 → CI 构建并发布 | ✅ 直接借鉴 |
| 产物命名 **含版本与平台**，且与安装脚本对齐 | hestiacp 的 `install.sh` 按 `hst-release` 下载固定名产物 | ✅ 直接借鉴：`zhiweipanel-<version>-linux-<arch>` 必须与 `deploy/install.sh` 的 `BIN_URL` 示例一致 |
| **校验和**随产物发布 | GoReleaser 标准形态：`checksums.txt`（SHA-256） | ✅ 直接借鉴 |
| Release notes **自动生成** | `gh release create --generate-notes` 按提交区间生成 | ✅ 直接借鉴 |
| **旧产物清理**：只删附件、保留 Release 记录 | 通行做法 | ✅ 直接借鉴（与本仓库声明的「只保留最新程序包」发布策略一致） |
| 安装脚本与产物**版本号单一来源** | hestiacp 用变量注入 | ✅ ZhiweiPanel 已有 `internal/version` 门禁，本轮把 `release.yml` 也纳入「零硬编码版本」约束 |

**明确不借鉴的**：
- ❌ **GoReleaser 工具本身**：引入一套配置文件 + 语义化提交检查，对本项目 2 个构建目标来说过重；原生 `go build` 循环 + `gh` CLI 已覆盖全部需求。
- ❌ **GHCR 镜像发布**：本项目 Docker 部署走 `docker compose up -d --build` 源码构建，测试机也是这么跑的；发布镜像会引入「多清单镜像清理」这一整类风险（provenance/sbom 产生的未打 Tag 子清单，误删会破坏当前镜像），在没有真实用户拉取需求前是纯负债。
- ❌ **Windows / macOS 二进制**：面板以 root 管理 nginx，依赖 systemd 与 `/proc`，桌面系统上没有运行形态。构建它们只会产出「能启动但必然不工作」的产物。

### B. 站点安全操作的一级 UI 入口（下一轮 P0）

**来源**：`1Panel` / 宝塔把「安全基线」「API 密钥权限」做成一级界面操作，而不是藏在 API 文档里。

**对应本项目 README「已知限制」#14 与 #15**（短板已自认）：

| 已知限制 | 现状 | 落地方式 | 优先级 |
|------|------|---------|--------|
| #14 防篡改基线只有 API 没有界面 | `POST /api/sites/{id}/baseline` 存在，前端无按钮；不建基线就开篡改告警会持续误报 | 站点详情安全页签加「建立基线」操作 + 二次确认 | P0 |
| #15 `shell` scope 只能通过 API 授予 | 运维中心 Token 弹窗只有「只读 / 可写」两档 | Token 创建弹窗增加 `shell` 档 + 风险提示文案 | P0 |

两项都是**用户可见功能** → 下一轮应走 **minor** 版本。⚠️ 注意：`0.2.0 ~ 0.2.2` 已被
版本线重置前的旧线占用（`internal/version` 的 `History` 已登记），下一轮 minor 建议
**直接跳 `0.3.0`**，避免 CHANGELOG 出现两个语义不同的 `v0.2.0`。

### C. 面板可被 AI agent 安全操作（下一轮 P1）

**来源**：`goinfinite/os` 的 `SKILL.md` + `AGENTS.md` 范式（v0.2.2 已列为候选，本轮维持）。

- ZhiweiPanel 已有 API Token（read / write / shell 三档 scope）与完整 REST API，
  缺的是「一份权威、结构化的操作说明书」：哪些端点有副作用、哪些字段服务端决定、
  常见危险操作的调用顺序。
- 落地方式：`docs/AGENT.md`（面向机器的 API 速查 + 安全注意事项），零代码改动。
- 非用户可见功能 → 可随任意版本发布。

### D. 审计导出 CSV / JSON（下一轮 P1）

**来源**：等保合规的通用报表需求；`1Panel` 提供日志导出。

- 审计表已有 5000 条留存与完整字段（谁/何时/动了什么/结果码/来源 IP），
  差一个 `GET /api/audit-logs/export` 端点 + 流式 CSV 输出。
- 小工作量；注意导出属于**读操作**但会带出敏感字段，必须复用现有鉴权中间件。

### E. 2FA / TOTP 与配置漂移主动告警（下一轮 P2）

维持 v0.2.2 结论（见其第五节），本轮无新增信息：
- 2FA/TOTP：单管理员场景优先级低于运维层，中等工作量。
- 配置漂移主动告警：快照 diff 能力已具备，差一个定时比对 + 通知渠道接线，中等工作量。

## 三、明确不借鉴的（连同理由）

| 能力 | 同类项目 | ZhiweiPanel 不做 | 理由 |
|------|---------|------------------|------|
| 容器应用商店 / 编排 | CasaOS、coolify、dokploy | ❌ | README 已声明刻意不做；收窄功能面是本项目的核心取舍 |
| 监控 agent 架构 | beszel（server+agent 分离） | ❌ | 单机面板不值得多一个常驻 agent；`/proc` 直读零依赖 |
| 终端 / PTY | 1Panel、hestiacp | ❌ | v0.2.2 已排除：root shell 暴露到 Web，与「只做网站管理」冲突 |
| 完整文件管理器 | filegator 等 | ❌ | 已有站点级文件管理，完整 FM 是独立产品 |
| 防火墙管理 | 1Panel、hestiacp | ❌ | 与宿主机安全组职责重叠 |
| 多租户 / RBAC | coolify、hestiacp | ❌ | 定位是单机单管理员 |
| GHCR 镜像发布 | 1Panel、usememos | ❌（暂缓） | 部署形态是源码构建；无真实拉取需求前引入镜像清理风险不划算 |

v0.2.2 的排除表（gopsutil / 阻塞采样 / MonitorDB / 规则 DSL / 独立审计库）继续有效。

本轮（v0.1.4）是项目公开后的**首个带 Tag 与 Release 产物的版本**，内容以修复为主：

| 项 | 来源 | 产物 |

以上均为修复 / 发布工程，**无新增用户可见功能**，故版本号走 patch（0.1.3 → 0.1.4）。

## 七、一句话结论

> 功能层（站点管理 19 页签）经 v0.2.2 轮对比**不落后**于 1Panel 等同类；
> 本轮补齐的差距是**交付层**——项目公开后还没有可下载的 Release 产物，
> `v0.1.4` 用一条 tag 触发的流水线把「源码」变成「可安装的版本化产物」。
> 下一批差距在**安全操作的 UI 化**（基线建不了、shell 授权点不出来），
> 这两项是当前仅有的「功能存在但用户够不着」的断点。
